# ADR-022: Automated version ladder

Date: 2026-08-30 · Status: Superseded by [adr/025](025-standard-release-flow.md)
(2026-10-05) — the automated ladder was retired; versions are bumped by humans
via `cargo xtask bump`. Decision text below kept as a record.

## Context

adr/021 left versioning manual: "bump `version` in the promotion PR" was a
checklist item, nightly carried whatever version the last promotion left, and
the example atoms + spec tables drifted (atoms still showed 0.7.0 at 0.8.0).
The owner wanted merges to encode readiness, not clocks — but the *version*
should follow the merges mechanically. Settled ladder:

- every merge into **nightly** → patch (`X.Y.Z → X.Y.Z+1`);
- every promotion (**nightly → main**) → minor (`X.Y.Z → X.(Y+1).0`),
  which is the released stable;
- **major** → reserved for critical/official changes, manual (not wired into
  CI; revisit when the first one is wanted).

Three hard constraints shaped the mechanics:

1. **`main` is frozen** (branch protection, `enforce_admins`, required
   checks): nothing may push to it, so the version a promotion releases must
   already be inside the PR's head (`nightly`).
2. **`GITHUB_TOKEN` pushes never trigger workflows** (recursion guard), so a
   token-made bump commit cannot re-run PR checks — and a bump pushed *after*
   a merge won't be in the artifact that merge's run builds.
3. **`nightly` is unprotected** (the owner direct-pushes generated-surface
   fixes), so bots may push bump commits to it directly.

## Decision

One mechanical step — `cargo xtask bump patch|minor|major|--to X.Y.Z` — is
the single implementation of "bump the version everywhere": both manifests,
`Cargo.lock`, the three version-bearing example atoms (`register`,
`link register`, `upgrade`), and every generated surface (`howto.gen.md`,
spec tables — regenerated by a *subprocess* `cargo xtask build`, because
`env!("CARGO_PKG_VERSION")` is baked in at compile time). Git stays with the
caller. Three automation points in `release.yml`/`ci.yml`:

- **patch ladder** (`bump` job, first on every nightly push): bump → commit
  `chore(release): bump to X.Y.Z` → push with `GITHUB_TOKEN` (no cascade, by
  constraint 2) → *the same run* builds the bumped sha and rolls the nightly
  prerelease, so the canary artifact reports the new version. The bump job
  runs the strict build itself — a broken trunk fails before anything ships.
  **Pause window:** while a nightly→main PR is open, the ladder skips (a late
  patch bump would move nightly past the release minor and fail the guard).
- **promotion bump** (`promote-bump` job, on PR open/reopen): the
  **release-bot GitHub App** pushes `--to <main's minor+1>.0.0` onto nightly.
  An App token is required (constraint 2): its push fires `synchronize`, so
  the PR's required checks re-run. `ci.yml`'s guard enforces the exact
  version — the bot is the convenience, the guard is the rule.
- **recut** (`recut` job, after a main push publishes stable): fast-forward
  `nightly` to the promotion merge, so the trunk absorbs main's merge commit
  and the ladder resumes at `X.(Y+1).1`. FF-only — if nightly moved in
  between, the job fails loudly and the owner reconciles via a PR.

Version-bearing atoms are rewritten by whitelisted `d+.d+.d+` replacement —
a full `--capture-example` re-run would clobber hand-authored behavioral
notes and rewrite `upgrade`'s real GitHub-URL envelope against a CI fixture.
Other atoms (venv) embed *package* versions and are never touched.

## Consequences

+ One command, one commit type, zero human version bookkeeping below major.
+ Every surface that shows the version moves together (compile-time
  `env!`, generated specs, atoms, lock, release tags).
+ The nightly canary always reports a version strictly newer than stable.
− Ops prerequisite: the release-bot App + `RELEASE_BOT_APP_ID` /
  `RELEASE_BOT_PRIVATE_KEY` secrets must exist or promotions fail loudly.
− A promotion open while feature PRs land holds the patch ladder (they
  resume on merge); merges in the promote→recut window make recut red until
  reconciled (deliberate: fail loudly, never force).

## Rejected

- **Version stamps at build time (no commits)** — the repo would lie about
  its version between merges; `upgrade --source` builds would mismatch.
- **GITHUB_TOKEN bot for the promotion bump** — its pushes don't re-run PR
  checks (constraint 2), leaving the PR unmergeable on stale checks.
- **Bumping inside feature PRs** — every PR would conflict on `Cargo.toml`.
- **Force-pushing the recut** — would silently discard nightly-only commits;
  FF-or-fail keeps the "promotion absorbs drift" rule of adr/021 honest.
